# ADR 0002 — Compile the vendored XSDs to static tables

* **Status:** Accepted
* **Date:** 2026-11-12
* **Decision owners:** project maintainers
* **Supersedes:** —
* **Superseded by:** —

## Context

L2 conformance is defined by the official XSDs (`Schema_VFPR12_v1.2.3.xsd` and the FSM10
1.0.2 schema). The validator must check element order, cardinality, `sequence`/`choice`,
enumerations, patterns, lengths and numeric ranges (PLAN §1.1). It must do so offline, in
one streaming pass, without a DOM and without a runtime regex engine (PLAN §2.2–§2.4).

A general-purpose XSD engine is large, interprets the schema at runtime, usually drags in
C/libxml2 (rejected by [ADR 0001](0001-pure-rust.md)), and makes the validation surface
depend on engine quirks. The invoice schemas are comparatively small and stable: the plan
notes they are mostly `sequence` plus `simpleType` facets, and records the immature
pure-Rust XSD tooling as risk R3 with a fallback of a custom reader.

## Decision

The official XSDs are **vendored** into `crates/fattura-core/data/` with provenance and
checksums, and are **compiled at `xtask` time** into static Rust tables:

* the structural model (elements, order, cardinality, choices, type references);
* closed enumerations and effective-dated tables;
* simple-type facets (lengths, ranges, whitespace);
* XSD patterns compiled to small hand-written matchers, not a runtime regex engine.

`fattura-core` contains **no XSD parser and no runtime XSD interpretation**. Generated
files are committed, reviewed and regenerated by `xtask`; a schema update is a PR that
includes the new XSD, its checksum/provenance entry, the regenerated tables and any
snapshot changes. Unsupported XSD constructs fail the generator loudly rather than being
silently skipped. `xmllint --schema` is used in CI only as a differential oracle, never as
a dependency (PLAN §7.2).

## Alternatives rejected

### Runtime XSD engine

Rejected: requires a C library or a large pure-Rust engine, builds a DOM, is slower than a
streaming walk, introduces a large untrusted parser/engine surface, and makes behaviour
depend on the engine's XSD support. It also conflicts with the WASM and no-C constraints.
Schema interpretation at runtime would still need a pattern engine, so it does not remove
the hard parts.

### Schematron

Rejected as the primary mechanism: the sources currently believe there are no official
Schematron/XSD 1.1 assertions (PLAN §11, question 8), so it is not the normative oracle.
A Schematron pipeline would add an XSLT/engine dependency and an extra dialect without
covering the XSD structure. If official assertions are later found, they can be cited and
encoded as additional generated checks; that does not require a runtime Schematron engine.

### Hand-written structural checks only

Rejected: it drifts from the XSD, misses facets and cardinality, and cannot credibly
implement control `00200`. The XSD is the normative structural definition; hand-written
checks may supplement it for cross-field rules, not replace it.

## Consequences

* **Positive:** L2 is fast, deterministic, allocation-light and WASM-friendly; no schema
  file is read at runtime; the schema version is fixed at build time.
* **Positive:** the schema surface is explicit and reviewable, and a schema update is a
  visible diff with provenance.
* **Negative:** the project owns a code generator and must track XSD features it does not
  support. Adding a new schema version requires `xtask` work and re-validation.
* **Negative:** XSD regular-expression semantics (`\i`, `\c`, Unicode blocks, anchors,
  whitespace) must be reproduced by the generated matchers and covered by differential
  tests; documented relaxations are allowed only as a known-difference list.
* **Follow-up:** E3.1 vendors the XSDs, E3.2 builds the generator, E3.3 the facet engine,
  E3.4 the structural walk, and E3.5 the differential suite. Generated code is excluded
  from coverage only where it is mechanical and reviewed.
